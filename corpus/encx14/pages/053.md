# 53 Brown-out events in the field

## 53.1 How they happen

In a robot joint the encoder often shares the 3.3 V rail with the logic
that drives the motor. A step in motor current can pull the rail below
VBOR = 2.6 V for a few microseconds. A dip longer than the brown-out filter
time tBOR (typ. 2 µs, page 11) resets the device.

## 53.2 What the host sees

  - No bus error. The I²C interface is ready 1.5 ms after the reset; a read
    that falls inside that window is NACKed, later reads succeed.
  - The angle keeps arriving. It is valid again 2 ms after the reset.
  - STATUS.RST = 1 on the next STATUS read, then 0 again.
  - CONF2 = 0x00: FILT = 0, DIR = 0, HYST = 0, WD = 0.

The joint keeps moving, but with the filter off. Velocity noise rises by a
factor of about 5 (table 48-1). Tracking error and motor current rise, the
joint may buzz. If the host relied on DIR = 1, the feedback sign reverses.

## 53.3 Detecting a brown-out

The only reliable evidence is STATUS.RST. Read STATUS on every control
cycle with the 3-byte burst read from 0x0B (page 40) and test bit 0. A
host that reads STATUS only at start-up will not detect a brown-out.

Indirect evidence, useful when analysing logs after the fact:

  - A step increase in angle noise or velocity noise with no mechanical
    change.
  - A single NACK on the encoder address during a motor current step.
  - A coincidence between motor current steps and the change in noise.

## 53.4 Required response

In the same control step in which RST = 1 is read, rewrite CONF2 (page 45,
errata E-3 on page 58). Count and log the event. If the count rises over
time, improve supply decoupling (page 17); do not rely on decoupling alone.

## 53.5 Frequency

Field data from robot joints with shared supplies shows brown-out rates
from less than one per year to several per hour, depending on layout and
motor current. A design must assume that brown-outs happen.
